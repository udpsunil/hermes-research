Lesson 2: The Controller Block Diagram

Weekend 1, Sunday session · ~60 min · Mission: become an SSD debug architect

Today's win: You will draw, from memory, the block diagram of an SSD controller with every major block labeled and the three data paths traced through it. This diagram is the map you'll use for every debug session in this course.

1. What the controller actually is

The controller is a small computer built for one job: make dumb, weird NAND look like a reliable block device to the host. It is usually an ARM-based SoC with specialized hardware accelerators attached. Everything on the board except the NAND dies and the DRAM lives inside this one chip.

2. The blocks

BlockJobDebug lens: what breaks
Host interface (PCIe/NVMe or SATA)Speaks the host protocol, moves data over the busLink training failures, NVMe timeouts, surprise link-down
CPU cores (2–8 ARM cores)Run the firmware: FTL, command scheduling, wear levelingFirmware bugs, race conditions, CPU saturation under load
ECC engine (LDPC/BCH)Corrects bit errors on every read; generates parity on writeUncorrectable errors when RBER exceeds correction capability
NAND controllers (one per channel)Drive the NAND dies: page reads, programs, erasesChannel contention, die timeouts, program failures
DRAMHolds the FTL mapping table and write buffersMapping loss on power cut without capacitor support
Power-loss protection (capacitors)Hold-up energy to flush buffers during a power cutCorrupted FTL after unsafe shutdowns; failed caps
Boot ROMFirst code that runs; loads firmware from NANDBricked drives from bad firmware updates

3. The three data paths

Trace these three paths on your diagram. Every performance or data-integrity bug lives on one of them.

Write path

Host → host interface → CPU (FTL decides where) → write buffer (DRAM)
    → NAND controller → ECC parity generated → program page on die

Note the data sits in volatile DRAM briefly. If power dies here, the capacitor must carry the flush. No capacitor, no guarantee.

Read path

Host → host interface → CPU (looks up mapping) → NAND controller
    → read page → ECC engine corrects → DRAM buffer → host interface → host

Latency here is your read-latency debug target. Mapping lookup, die access, and ECC decode time stack up.

Internal path (garbage collection)

CPU decides block is garbage-heavy → read valid pages → write them
    elsewhere (through ECC again) → erase the block

This traffic never touches the host. It competes for the same channels and dies as host I/O. That competition is why full drives get slow.

4. Parallelism: channels and ways

A drive gets its bandwidth from running many dies at once. Eight channels, four dies per channel means 32 dies working in parallel. The controller interleaves pages across them. When you debug a bandwidth problem, you ask: are all channels busy, or is traffic piling up on a few? The Cactus Tech primer covers this well.

Check your understanding

Q1. Why does the mapping table live in DRAM and not in the controller's internal SRAM?

Q2. Garbage collection traffic slows host I/O because it competes for what?

Q3. A drive loses its mapping table after a power cut. Which block failed first?

Do this now (45 min)

Draw the diagram yourself. Blank paper, pen, no reference. Requirements:

  1. All seven blocks from the table, placed roughly where data flows
  2. NAND dies drawn as groups of 4 hanging off 8 channel lines
  3. DRAM connected with a note saying what lives in it
  4. Three arrows in different colors: write path, read path, GC path

Stuck on a block? Peek at the glossary or the alvinrolling article, then close it and draw from memory again. The struggle is the point.
