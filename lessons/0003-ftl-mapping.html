Lesson 3: FTL Part 1 — Mapping

Weekend 3 · Saturday session · ~60 min

Today's win: You will explain how the FTL mapping table works, why page-level mapping needs DRAM, why block-level mapping is cheap but slow, and how hybrid schemes split the difference. You will also calculate the DRAM cost of a mapping table for a real drive.

1. What the FTL actually does

The host sends a write to LBA 1,004 (a logical address). NAND has no concept of LBA. The FTL maintains a translation table: logical block address → physical NAND location. Every read, every write, every trim goes through this table.

The FTL has four jobs. Today we focus on mapping. The others: wear leveling, garbage collection, bad-block management.

2. Three mapping schemes

Page-level mapping

One table entry per logical page. Flexible: any physical page can hold any logical page.

Pros: maximum performance, minimal write amplification.

Cons: the table is huge.

Math. A 1 TB drive with 4 KB pages = 256 M logical pages. Each entry stores a physical page address: typically 4–8 bytes (die, plane, block, page). Say 8 bytes. 256 M × 8 B = 2 GB of RAM just for the table. That needs DRAM, not SRAM. Expensive. Possible, but expensive.

Block-level mapping

One table entry per logical block (block = 64–512 pages). The controller tracks which logical block lives in which physical block and which offset inside it.

Pros: tiny table. 1 TB drive ÷ 4 MB blocks = 256 K entries × 8 B = 2 MB of RAM.

Cons: whenever the host writes a single page, the entire block containing that page must be relocated. High write amplification. Wasteful.

Hybrid mapping (most common)

Block-level mapping for the top-level table, plus a small per-block log buffer (often 2–4 pages) where incoming writes land. When a log block fills, the controller merges it back into the parent block.

Pros: cheap table + most writes handled in the log. Real-world drives use variants of this.

Cons: merge operations still cause write amplification. Complexity lives in the merge policy.

3. The mapping table lives in DRAM

On power loss, the mapping table is rebuilt from NAND by scanning. This takes time and is why drives have a "first access slower" behavior after a cold boot. Drives with power-loss capacitors can flush the table periodically and restore it faster.
