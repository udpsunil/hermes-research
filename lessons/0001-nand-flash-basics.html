Lesson 1: NAND Flash Basics

Weekend 1 · Saturday session · ~45 min · Mission: become an SSD debug architect

Today's win: You will be able to explain — from memory — why an SSD cannot overwrite data in place, and trace that single physical constraint to garbage collection, write amplification, and half the weird latency behavior you'll ever debug.

1. The one constraint that explains everything

A hard disk can overwrite a sector in place. NAND flash cannot. Inside a NAND chip:

  • You read and write (program) in units of a page — typically 4–16 KB.
  • You erase in units of a block — a group of 64–512 pages, several MB.
  • Erasing sets every cell in the block to its starting state. Programming only raises a cell's threshold voltage — it can never lower it back.
So to change even one byte of a written page, the SSD must copy the valid pages of the block elsewhere, erase the whole block, then write. This is erase-before-write — the root cause behind garbage collection, write amplification, and the FTL itself.

2. Cell types: trading bits for endurance

Each cell stores charge levels; more levels per cell = more bits, but the voltage states sit closer together, so misreads and wear accumulate faster.

CellBitsP/E cyclesWhere you see it
SLC1~100KIndustrial, write caches (pSLC)
MLC2~3–10KLegacy enterprise
TLC3~1–3KMainstream SSDs today
QLC4~300–1KCheap high-capacity drives

Debug lens: when a drive shows early wear-out or high raw bit error rates, the first question is what NAND is in it? A QLC drive at 500 P/E cycles is behaving normally; an SLC drive at 500 is broken.

3. Where errors come from

NAND errors are not bugs — they're physics. Four sources you'll chase your whole career:

  1. Wear — oxide degrades with every P/E cycle, charge leaks faster.
  2. Read disturb — reading a page repeatedly nudges neighboring cells' voltages. Mitigated by periodically rewriting blocks.
  3. Retention loss — charge leaks over months; hot drives and worn cells lose it fastest.
  4. Program disturb — programming one page perturbs its neighbors in the same block.

The controller hides all of this with ECC (LDPC/BCH). Your telemetry signals: RBER (raw bit error rate, pre-ECC) trending up = wear or disturb; UBER (uncorrectable) = real data corruption.
